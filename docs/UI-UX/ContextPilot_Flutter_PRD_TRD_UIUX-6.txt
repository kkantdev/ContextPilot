# 1. PRODUCT OVERVIEW

ContextPilot is a phone-first AI developer agent.

The Flutter application is the mobile control center. It allows a developer to connect to a ContextPilot Agent running on their laptop and use natural language to inspect, understand, modify, test, and secure a software project.

The Flutter app does NOT directly access the laptop filesystem.

The Flutter app communicates with the laptop-side ContextPilot Agent over the local network using the ContextPilot communication protocol.

Conceptual architecture:

Phone
  ↓
Flutter ContextPilot App
  ↓
Local network
  ↓
ContextPilot NPM/Laptop Agent
  ↓
Project files / terminal / Git / tests / local AI

The Flutter app is responsible for:
- User interaction
- Pairing
- Connection state
- Conversation
- Operation approval
- Progress display
- Results
- Project overview
- Git/change review
- Security findings
- Voice input where supported
- Clear safety boundaries

---

# 2. PROBLEM

Developers often need to repeatedly switch between:
- IDE
- terminal
- project files
- Git
- test output
- documentation
- AI assistants

Existing AI coding assistants are usually centered around the desktop IDE.

ContextPilot explores a phone-first workflow where the developer can request development actions from the phone while the laptop-side agent performs controlled operations on the actual project.

The key problem is not simply "chat with AI."

The problem is:
How can a developer use a phone as a practical control center for a real software project without giving an AI uncontrolled access to the computer?

---

# 3. VISION

Make the phone a secure, understandable, and useful control surface for AI-assisted software development.

The desired experience:

"Tell ContextPilot what I want → understand the plan → approve important actions → watch the laptop agent work → review the result."

---

# 4. GOALS

## Primary goals

1. Connect a phone to a laptop-side ContextPilot Agent.
2. Make pairing simple using a QR code.
3. Show connection and project status clearly.
4. Allow natural-language developer requests.
5. Display the AI's understanding/plan.
6. Require approval for meaningful file changes or risky operations.
7. Show operation progress in real time.
8. Show created/modified files.
9. Show test/build results.
10. Show Git changes.
11. Display security findings.
12. Provide a polished phone-first hackathon experience.

## Secondary goals

- Voice input.
- Project health summary.
- Conversation history for the current session.
- Quick actions.
- Project context summary.
- Human-readable technical explanations.

---

# 5. NON-GOALS

Do NOT implement these in the initial Flutter MVP:

- Full desktop/Windows application.
- Cursor integration.
- VS Code extension.
- Cloud backend.
- User accounts.
- Social features.
- Billing/subscriptions.
- Remote internet access.
- Multi-user collaboration.
- Full IDE/editor inside the phone.
- Direct unrestricted filesystem access.
- Direct execution of shell commands from the phone.
- Permanent cloud storage of project code.

The phone must communicate through the ContextPilot Agent.

# 7. CORE USER STORY

As a developer, I want to open ContextPilot on my phone, pair it with my laptop, select the active project, describe what I want in natural language, review the proposed actions, approve them, and monitor the work without needing to manually perform every repetitive development task.

Example:

"Create an authentication feature for this project."

ContextPilot:
1. Understands the project.
2. Creates a plan.
3. Shows files that will change.
4. Requests approval.
5. Sends approved actions to the laptop agent.

# 11. CONNECTION & PAIRING LOGIC

The QR code is a pairing mechanism, not the communication transport.

Expected model:

Phone
  ↓ scans QR
Connection payload
  ↓
Phone opens local connection
  ↓
Authentication/pairing
  ↓
WebSocket/HTTP communication
  ↓
Connected

Same local network is the initial expected environment.

Possible network:
- Wi-Fi router
- compatible local hotspot

Do not assume internet access.

The app should not require cloud connectivity for the core connection.

The exact networking implementation belongs to the NPM agent and shared protocol specification.

---

# 12. AGENT INTERACTION MODEL

The Flutter app should treat the laptop agent as an external capability provider.

The Flutter app must NOT directly execute:
- shell commands
- filesystem operations
- Git commands

Instead:

Flutter
→ sends intent/request
→ Agent
→ validates/executes
→ Agent sends events/results
→ Flutter renders them

The UI should never pretend an action succeeded before receiving confirmation.

---

# 13. AI INTERACTION MODEL

The user should interact primarily through natural language.

Example prompts:

- "Analyze this project."
- "Why is the build failing?"
- "Create an auth feature."
- "Find unused dependencies."
- "Run the tests."
- "Review my latest changes."
- "Check this project for security problems."

The Flutter app does not need to know the internal model provider.

The app should communicate with the agent through abstract AI/agent events.

This allows the laptop agent to use:
- local/open-source model
- future on-device model
- optional cloud fallback

without requiring UI changes.

---

# 14. APPROVAL & SAFETY MODEL

This is a core feature.

Every operation should have a risk level supplied by the agent.

Suggested categories:

SAFE:
- project metadata
- read/search
- git status

REVIEW:
- create file
- modify file
- install dependency
- run tests/build

DANGEROUS:
- delete files
- destructive shell commands
- reset/revert operations
- potentially destructive project/database actions

The Flutter app must visually distinguish risk.

Approval screen should show:

- What will happen
- Files affected
- Commands if applicable
- Risk level
- Approve
- Reject
- Cancel

Never use a vague "Continue" button when the operation has destructive consequences.

# 17. ERROR & EDGE CASES

Handle:

## Connection
- Wi-Fi unavailable
- Laptop unreachable
- Agent stopped
- Pairing token invalid
- QR invalid
- Protocol mismatch
- Connection timeout
- Connection dropped

## Operation
- Permission denied
- File no longer exists
- File changed externally
- Command failed
- Test failed
- AI unable to produce a safe action
- Operation cancelled

## UI
Never leave the user with an indefinite spinner.

Every long-running operation needs:
- status
- cancel option when supported
- failure state
- retry where appropriate

# 27. SECURITY & PRIVACY

Core principles:

1. No account required for MVP.
2. No cloud storage of source code.
3. Local network first.
4. Pairing token required.
5. Connection must be authenticated.
6. Sensitive tokens stored securely on phone.
7. Never display secrets unnecessarily.
8. Never automatically approve dangerous operations.
9. Show user what will change.
10. Disconnect must invalidate/revoke the session as appropriate.

The phone should clearly communicate:
"Your project remains on your laptop."

---

# 28. PERFORMANCE

Target:
- fast app startup
- responsive UI
- smooth QR scanning
- low-latency connection status
- real-time operation events
- no blocking UI during long operations

Large logs should be streamed/paginated rather than rendering unlimited content.

Avoid loading entire repositories into phone memory.

# 29. OFFLINE / DISCONNECTED BEHAVIOR

"ContextPilot Agent disconnected."

- viewing previously loaded local UI state
- viewing recent activity cached locally where appropriate
- reconnect

Do not pretend AI/project operations are available when the agent is offline.

# 35. IMPLEMENTATION RULES FOR AI CODING AGENT

CRITICAL RULES:

1. Inspect the actual Flutter project before making changes.
2. Do not invent files or dependencies.
3. Do not install unnecessary packages.
4. Keep features modular.
5. Do not implement the NPM agent inside the Flutter project.
6. Do not implement a Windows GUI.
7. Do not integrate Cursor unless explicitly requested later.
8. Do not create a cloud backend for the MVP.
9. Do not bypass the approval system.
10. Do not expose unrestricted terminal/file access to the Flutter UI.
11. Do not store source-code repositories unnecessarily on the phone.
12. Keep protocol code isolated from UI.
13. Use mock/local protocol adapters during Flutter development if the NPM agent is not yet available.
14. Clearly label mock data and do not confuse it with real agent responses.
15. Keep the UI production-quality but prioritize functional flows.
16. Every asynchronous operation must have loading, success, failure, and cancellation/recovery states where applicable.
17. Never expose model chain-of-thought. Display only concise reasoning summaries, plans, actions, and results.
18. Follow the existing project's actual architecture if this document is introduced into an existing codebase; do not rewrite unrelated code.
19. Before adding a dependency, verify that it is necessary.
20. The final Flutter app should be capable of operating as the phone-side client independently from the NPM agent implementation.
